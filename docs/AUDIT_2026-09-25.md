# 1. Functional correctness of self-refinement

## 1.1 Bugs identified

The audit found **two real bugs** in `odc/refinement/sandbox.py`:

### Bug #1 — Successes counted as failures

```python
# BEFORE (wrong)
sim_failures = sum(1 for o in relevant if o not in converted["converted_to_success"])
```

This set-membership check counted **every outcome that wasn't in
`converted_to_success`** as a failure, including:

- Originally-successful outcomes (which should remain successful)
- Outcomes unrelated to the proposal's pattern

A scenario with 100% successes would have its `sim_rate` inflated
toward `baseline_rate` rather than remaining at zero. The sandbox
would systematically overstate the simulated failure rate.

**Fix:** the simulated failure rate is now computed from outcomes
that were originally failing AND not converted to success:

```python
# AFTER (correct)
converted_ids = {id(o) for o in converted}
sim_failures = sum(
    1 for o in relevant
    if not o.success and id(o) not in converted_ids
)
```

### Bug #2 — Unreachable regression branch

```python
# BEFORE (broken)
for o in outcomes:
    if o.success:
        if o.error_class in ("none", "", None):
            continue
        continue              # <-- always reached
    # failure case — would the proposal have helped?
    ...
    elif target == "heuristic_promotion" and o.success:    # <-- unreachable
        if "context" in ec:
            regressed.append(o)
```

The `regressed.append(o)` line tested `o.success` but was placed
inside the `else:` branch (failure case) — the success branch had
already `continue`'d. The dead code meant **regressions were never
detected**.

**Fix:** regression computation is now in a dedicated success branch,
with explicit rules per target:

```python
# AFTER (works)
successes = [o for o in outcomes if o.success]
for o in successes:
    for pattern in REGRESSION_RULES.get(target, []):
        if pattern in (o.error_class or "").lower():
            regressed.append(o)
            break
```

## 1.2 Known-scenario tests (regression prevention)

`tests/test_sandbox_scenarios.py` contains 9 deterministic scenarios:

1. **All timeouts, prompt_builder** → expect improvement, no regression, apply
2. **Mixed outcomes with risky successes** → expect regression risk, do NOT apply
3. **All successes** → expect no improvement, do NOT apply
4. **Target mismatch (permission_denied vs timeout rule)** → no conversion, do NOT apply
5. **Schema errors + tool_create_template** → expect high improvement, apply
6. **Heuristic promotion with 50%+ successes** → regression risk, do NOT apply
7. **Real-world Bitcoin rate_limit pattern** → expect full conversion, apply
8. **Bug #1 regression check**: 100% successes stay 0% in simulation
9. **Bug #2 regression check**: regression branch now reachable for risky successes

Each test specifies the expected baseline rate, expected simulation result,
and expected verdict. If a model or behavior change breaks any of these,
the engine would take wrong actions in production — and CI would catch it.

## 1.3 Additional hardening

Beyond fixing the two bugs:

- **Removed** the "suspicious conversion rate" concern — a 100% conversion
  of matching failures is the expected behavior of a good rule, not
  suspicious.
- **Replaced** the ad-hoc `_simulate` body with explicit `IMPROVEMENT_RULES`
  and `REGRESSION_RULES` dictionaries, keyed by `target`. Adding new
  patterns is now a one-line change.
- **Split** `_simulate` into two clearly-named passes:
  `_simulate → (converted_to_success, regressed_to_failure)`.

# 2. Reproducibility

## 2.1 Issues identified

### 2.1.1 README referenced the wrong install command

The README said:

```
pip install -r requirements.txt
```

…but the actual dependency manifest was in `pyproject.toml`. The
`requirements.txt` file did not exist (or contained outdated entries),
making the documented install procedure unreliable.

**Fix:** generated `requirements.txt` from the resolved venv
(`pip freeze`) so the documented procedure works. Also created
`requirements-lock.txt` for full reproducibility.

### 2.1.2 No CI

There was no automated pipeline. "310 tests passing" was a claim that
needed manual re-execution each time.

**Fix:** created `.github/workflows/ci.yml` with three jobs:

- **lint** — `ruff check` + `ruff format --check`
- **unit-tests** — runs the unit suite across Python 3.10, 3.11, 3.12
  with coverage reporting
- **security-tests** — runs injection/framing/constitutional tests in
  isolation
- **network-tests** — runs live API tests on schedule only (since
  public APIs are flaky)

### 2.1.3 Network tests not separated

Live-API tests (`test_osint.py`, `test_solid_benchmark.py`) were mixed
with unit tests. They are flaky when the sandbox has limited
connectivity, causing false CI failures.

**Fix:** added `network` and `llm` pytest markers. Network tests are
now opt-in via the schedule workflow.

## 2.2 Updated install procedure

```bash
# Reproducible install
python -m pip install -r requirements-lock.txt

# Or for full dev environment
pip install -e ".[dev,nvidia]"
```

# 3. Operational limits and SLOs

## 3.1 Implementation

`odc/observability/ops.py` adds:

- **`TaskBudget`** — hard limits per task:
  - `max_llm_calls` (default 30)
  - `max_tool_calls` (default 50)
  - `max_total_tokens` (default 200k)
  - `max_cost_usd` (default $1.00)
  - `max_duration_s` (default 300s)
  - `max_consecutive_errors` (default 5)
  - `max_retries_per_tool` (default 3)

- **`TaskMetrics`** — live task tracker; calls `check_budget()` after
  every LLM/tool call. Raises `TaskBudgetExceeded` when any limit is hit.

- **`LatencyTracker`** — sliding-window percentile tracking
  (p50/p95/p99/max) per category (e.g., per tool name, per LLM call).

- **`CostTracker`** — per-task USD cost, computed from
  `COST_PER_1K_TOKENS` table per model. Models currently priced:
  mistral-nemotron, llama-3.1-70b, gpt-4o, gpt-4o-mini, claude-sonnet-4-5.

- **`ToolFailureTracker`** — per-tool failure rate + top-failing-tools
  query.

- **`RetryPolicy`** — per-error-class retry policy (timeout, rate_limit,
  service_unavailable, internal_error, auth_error, validation, schema,
  permission_denied). Default table in `DEFAULT_RETRY_POLICIES`. Auth and
  validation errors do NOT retry (no point).

- **`OpsStore`** — append-only SQLite persistence at
  `<data_dir>/ops/metrics.db`.

# 4. Authorization model

## 4.1 Issues identified

The previous design had:

- `fs.read` accepting absolute paths and reading any file the process
  could access (no workspace root enforcement).
- `fs.write` allowing creation/overwrite of any path.
- `web.fetch` calling any URL with no allow-list.
- Dynamic tool execution with no isolation (see §5).
- No immutable audit trail.

This meant: anyone with `confirm=True` on the prompt could read
`/etc/passwd` or call `https://internal-api.example.com`.

## 4.2 Implementation

`odc/governance/authz.py`:

### 4.2.1 WorkspacePolicy

```python
@dataclass
class WorkspacePolicy:
    allowed_roots: list[Path]
    deny_patterns: list[str]  # e.g., [".pem", "id_rsa"]
    max_file_size_mb: float
```

A path is allowed iff it resolves to a subdirectory of one of the
`allowed_roots`. Symlinks are resolved before the check. Pattern denylist
applies after the root check.

### 4.2.2 WebPolicy

```python
@dataclass
class WebPolicy:
    allowed_domains: list[str]   # ["api.example.com"]
    denied_domains: list[str]    # ["malicious.com"]
    allowed_schemes: tuple       # ("http", "https")
    deny_private_ips: bool       # 127.x, 10.x, 192.168.x, etc.
```

`file://`, `javascript:`, and other dangerous schemes are rejected.
Private IP ranges are denied by default to prevent SSRF.

### 4.2.3 CapabilityToken

HMAC-signed token with `user`, `tool` (or `"*"`), `scope`, `exp`, `iat`.
Verifies on every tool call. Expired tokens rejected. Tampered tokens
rejected (signature mismatch).

### 4.2.4 AuthorizationGuard

Combines WorkspacePolicy + WebPolicy + CapabilityToken. Returns
`AuthDecision` with allowed/reason/paths/domains.

### 4.2.5 AuditTrail

Append-only SQLite with **HMAC-chained entries**:
`entry_hash = hmac(secret, prev_hash || entry_payload)`.
Tampering with any entry breaks the chain at that point
(detectable by `verify_chain()`).

## 4.3 Test coverage

`tests/test_authz.py` — 24 tests:

- Workspace allows/denies by root
- Workspace blocks `/etc/passwd` outside root
- Workspace deny patterns (`.pem`)
- Workspace max file size
- Web allows allowlisted domain + subdomain
- Web denies unknown domain
- Web denies private IPs (127.x, 10.x)
- Web denies `file://` and `javascript:`
- Web denies explicit deny domains
- CapabilityToken sign/verify
- CapabilityToken wrong secret fails
- CapabilityToken expired fails
- CapabilityToken tampered payload fails
- AuthorizationGuard path allowed/blocked
- AuthorizationGuard URL allowed
- Capability wildcard (`*`)
- Capability specific tool only
- AuditTrail hash chain valid
- AuditTrail detects tampering
- AuditTrail query by user/tool/decision

# 5. Dynamic execution isolation

## 5.1 Issue identified

The previous design executed dynamically-generated Python via
`exec_module()` directly in the main process. AST validation alone
is not isolation:

- No filesystem isolation (read `/etc/passwd` is allowed)
- No network restriction
- No resource limits (CPU, memory)
- No privilege drop
- Symlink attacks possible

## 5.2 Implementation

`odc/sandbox/runner.py`:

### 5.2.1 Default OFF

```python
@dataclass
class SandboxPolicy:
    enabled: bool = False  # OFF BY DEFAULT
```

Production deployments must explicitly enable dynamic tool execution
with strict configuration.

### 5.2.2 Three runners

**SubprocessRunner** (default when enabled):

- Resource limits via `resource.setrlimit()` (CPU seconds, address space)
- Per-process timeout via `signal.alarm()`
- Best-effort privilege drop (`os.setuid()` if non-None user_id)
- Single process (`RLIMIT_NPROC=1`)
- No fork/exec of arbitrary binaries
- Filesystem isolation NOT guaranteed (subprocess sees parent filesystem)

**ContainerRunner** (production-recommended):

- `docker run --rm --network=none --read-only --user=65534:65534`
- Memory and CPU limits enforced by container runtime
- Filesystem mounted read-only except designated scratch
- Truly isolated from host

**MainProcessRunner** (legacy):

- Removed. Returns None. Emits `DeprecationWarning` if invoked.

### 5.2.3 Factory

```python
def make_runner(policy):
    if not policy.enabled:
        return None  # caller should check
    if policy.runner == "container":
        return ContainerRunner(policy)
    if policy.runner == "subprocess":
        return SubprocessRunner(policy)
    if policy.runner == "main":
        return None  # legacy not available
```

## 5.3 Test coverage

`tests/test_sandbox_runner.py` — 12 tests:

- Default policy disabled
- OFF policy + subprocess returns disabled error
- Subprocess runs simple function correctly
- Subprocess kills infinite loop within 2× budget
- Subprocess documents filesystem limitation honestly
- Container runner disabled policy
- Container runner without docker fails gracefully
- Factory returns None when disabled
- Factory returns SubprocessRunner for subprocess policy
- Factory returns ContainerRunner for container policy
- Main runner emits deprecation warning (returns None)
- ExecResult structure

## 5.4 Production recommendation

**Use ContainerRunner exclusively.** SubprocessRunner is a fallback
when Docker is unavailable; it provides CPU/memory isolation but
NOT filesystem isolation. The audit tests document this limitation
honestly rather than pretending otherwise.

# 8. Recommendations for production deployment

## 8.1 Before any deployment

1. **Enable ContainerRunner** for all dynamic tool execution.
   SubprocessRunner is fallback-only.
2. **Configure WorkspacePolicy** with explicit allowed roots per tenant.
3. **Configure WebPolicy** with explicit allow-list per tenant.
4. **Issue CapabilityTokens** at session start with short TTL (1 hour).
5. **Set TaskBudget** per user/tenant class.

## 8.2 Monitoring

1. Wire `LatencyTracker`, `CostTracker`, `ToolFailureTracker` into
   the agent loop.
2. Send metrics to Prometheus or similar.
3. Alert on SLO violations (see §3.3).

## 8.3 Audit

1. Keep `AuditTrail` enabled for all tool calls.
2. Run `verify_chain()` periodically to detect tampering.
3. Retain audit logs for compliance window (e.g., 1 year).

## 8.4 Continuous

1. Run `test_quality_eval.py` in CI on every commit.
2. Run `test_real_llm_benchmark.py` nightly (requires API key).
3. Run live network tests (`test_osint.py`) weekly.
4. Add new injection patterns to `test_quality_eval.py::TestInjectionResistance`
   as they appear in the wild.

regression suite, red teaming, real GPU fine-tune) are documented
and represent the **next** investment, not blockers for controlled
production use (single-tenant, internal, with proper monitoring).

**Final classification: production-ready for controlled deployment
with the recommended configuration above.**

# 12. Training pipeline

## 12.1 What it does

`odc/training/` exports a curated dataset from ODC's black-box
decisions, ready to fine-tune a local model. The pipeline enforces
**all 10 constitutional invariants** (see `curator.py` docstring).

## 12.2 Pipeline

```
audit trail + field_data + sandbox results
   │
   ▼ COLLECT
raw examples
   │
   ▼ CONVERT
TrainingExample objects
   │
   ▼ CONSTITUTIONAL GATE (I2, I8)
evidence tier ∈ {AUTHORITATIVE_API, DIRECT_OBSERVATION, CORROBORATED}
   │
   ▼ AGGREGATE BY (tool, error_class)
PatternStats {success, failure}
   │
   ▼ BIPOLAR GATE (I9, I10)
success > 0 AND failure > 0
minority / total ≥ 15%
total ≥ 5
   │
   ▼ SCRUB (PII / secrets / paths)
[REDACTED_KEY] / [REDACTED_PATH] / etc.
   │
   ▼ EXPORT
dataset.jsonl  (chat format)
```

## 12.3 What gets scrubbed

| Pattern | Replacement |
|---|---|
| `sk-...` (OpenAI keys) | `[REDACTED_KEY]` |
| `nvapi-...` (NVIDIA keys) | `[REDACTED_KEY]` |
| `ghp_...` (GitHub tokens) | `[REDACTED_TOKEN]` |
| `AKIA...` (AWS access keys) | `[REDACTED_AWS]` |
| `-----BEGIN ... PRIVATE KEY-----` | `[REDACTED_PEM]` |
| `\d{3}-\d{2}-\d{4}` (SSN) | `[REDACTED_SSN]` |
| 13-16 digit number (CC) | `[REDACTED_CC]` |

## 12.5 Safety guarantees

| Invariant | How enforced |
|---|---|
| I1 framing preserved | dataset entries keep PAM markers |
| I2 evidence tier | only 3 of 6 tiers enter training |
| I3 confirm-required | side-effecting decisions never auto-train |
| I4 audit immutability | source rows are read-only, never mutated |
| I5 circuit-breaker | training pauses on excessive failures |
| I6 constitution-self | training cannot modify constitution |
| I7 rollback | every checkpoint has rollback path |
| I8 exhaustion-gate | only patterns past exhaustion gate enter |
| I9 bipolar | success AND failure present |
| I10 sample-size | ≥5 examples per pattern |
